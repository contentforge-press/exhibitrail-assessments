Exhibitrail · method

A review is a list of questions with answers attached.

Twenty-four tests in six classes. Each one asks something a security questionnaire actually asks, and states the evidence that settles it. If the evidence cannot be produced, that absence is the finding — not a missing checkbox.

Nothing here needs access to a running system beyond what is written into the scope. Nothing here is a payload.

1 · Instruction boundary

Can content the agent reads become an instruction it obeys?

#TestPass evidence
1.1Fetched content is delimited and labelled as data before it reaches the promptA boundary marker in the template; the system instruction says content inside it is data
1.2Tool output carries provenance into the message streamA field or type records origin — model text and tool text are distinguishable without guessing
1.3The system prompt is not reachable by askingA probe does not reproduce the instruction block; refusal is specific, not generic
1.4Instructions written into memory do not become behaviourA stored “from now on do X” is retrievable as a fact and not executed as a standing order

Fail shape: content and instruction arrive in the same string with no boundary, and the only defence is the model's judgment about what looks like an instruction.

2 · Action authority

What can the agent change without a human gate?

#TestPass evidence
2.1Write actions are enumerated, each with a gate or an explicit risk acceptanceA list exists, with the gate named per action
2.2The agent's credential is narrower than a human'sA scoped token, not a personal one; the scope is written down
2.3Irreversible operations are separated from reversible onesDelete, send, pay and grant are not in the same tool as read
2.4A gate cannot be skipped by a second pathThe same action through another tool, job or endpoint still hits the gate

Fail shape: one tool with broad credentials, and the protection is a sentence in the prompt telling the model to be careful.

3 · Memory isolation

Whose conversation can it read, and by whose name?

#TestPass evidence
3.1The tenant key is derived server-side, not supplied by the clientSession id minted or HMAC'd server-side; a client-supplied value is rejected
3.2Read paths authorise the caller before resolving the keyThe resolve function takes a principal, not just an id
3.3Namespace and metadata cannot be injected through configCaller config is rewritten or rejected at the boundary
3.4Deletion semantics are defined per store“Delete” names what it removes and what it leaves in backups

Fail shape: memory keyed by a value the end user can type.

4 · Retention

What is still stored after the session ends, and who can delete it?

#TestPass evidence
4.1Every store receiving user content is listedTranscript, vectors, logs, traces, provider-side — including the ones nobody owns
4.2Retention is configured per store, not left at defaultsA number of days per store, with the owner named
4.3Deletion is executable, not only documentedA delete path exists and has been run at least once
4.4Provider-side copies are disclosedThe model vendor's retention setting is known and stated

Fail shape: “we delete on request” with no runnable path, and logs that quietly outlive the policy.

5 · Sub-processor chain

Which third parties see the data, and is that disclosed?

#TestPass evidence
5.1Every sub-processor receiving content is listed by name and purposeA current list, not a category
5.2Telemetry and tracing vendors are included, not only model providersThe observability tool appears on the list
5.3The DPA set matches the listOne agreement per processor, or a stated exception
5.4Region of processing is statedWhere the data lands, for each processor

Fail shape: a sub-processor page naming model providers only, while traces and logs flow to three more vendors.

6 · Version lock

What pins the model and the prompt, so a verdict stays true next month?

#TestPass evidence
6.1The model identifier is pinned, not aliasedA dated or explicit version, not a family name
6.2Prompts are versioned artefactsA commit or hash per deployed prompt
6.3Dependencies are locked and scannedA lockfile plus a scan result with a date
6.4A re-test cadence is definedA date, or a trigger that forces one

Fail shape: “we use GPT-class models” and prompts edited in a console, so last month's verdict describes a system that no longer exists.

Four rules that are not configuration

  1. Candidates are never graded. Every scanner item stays Untriaged. The scanner's own severity goes into the body as an observation, never into the conclusion: “scanner says severity LOW, confidence HIGH — that is a pattern, not a verdict.”
  2. The same rule across files is one item. 13,499 assert calls in 342 files is one noise line, not 13,499 problems. Merged, 586 candidates became 99.
  3. Noise classes stay out of the body. Test-assert, temp-file and shell-pattern hits are filed in a CSV, not in the conclusion page, and the class names are printed when they fire.
  4. The body has a cap. Twelve items by default; the rest live in the CSV. A report nobody finishes is not a deliverable — finishing it is part of the work.

The human does one thing the tool cannot: turn Untriaged into High or withdrawn, and write the reason. A reason that cannot be written is a reason the item should not be in the report.

Five days, and what lands each day

DayWork
1Scope signed; inventory of surfaces taken; the eight engagement rules agreed in writing
2–3Static pass over the named surface, then targeted reading of the code paths each test names
4Each candidate answered: reachable under what condition, gated by what, or withdrawn and why
5Report, triage table, the 24-row pass/fail sheet, and a scope-and-limits page

What this refuses to do

No access to a live system
The work is done on source, a stated version, and documents. A deployed system is never touched.
No public demo
Public demos are someone else's property and outside any written scope.
No reusable payloads
Findings are written so they can be verified and fixed, not copied.
No CVSS ranking
Items are ranked by what a buyer can answer in a review, because that is the decision being made.
No score, no grade
A number invites comparison across systems that were not measured the same way. Counts are given as counts.
No attestation
No warranty, no statement on behalf of any maintainer, no claim that a certificate would not have made anyway.

What “Untriaged” and “withdrawn” mean

Untriaged
Confirmed to exist in the code, not yet decided whether it matters. It appears with the reason it is still open, not with a severity.
Withdrawn
Looked like a finding, then did not survive reading: the value is a constant, the path is unreachable, the flag is a test fixture. It is kept in the file with the reason, because a practice that hides its false positives cannot be checked.

To commission one

Send three things: the repository and the version to be reviewed; what the agent can change without a human approving it; and the date you need the answer.

Written scope comes back within 24 hours — eight rules of engagement, the surface named to the file, and what is explicitly out of bounds.

Writing only

No calls, no voice, at any stage of the engagement. Everything that would be said on a call is written into the scope or the report, where it can be re-read and quoted.
